第 2 页 · 存储引擎

InnoDB：MySQL 默认的事务型仓库

今天所讲的数据库系统原理基于 InnoDB 存储引擎。它是经典的关系型数据库存储引擎，也是目前使用最广泛的一种。

它从哪里来
  • 由 Heikki Tuuri 在芬兰 Innobase Oy 开发，约 1995 年起
  • 2001 年作为插件进入 MySQL 3.23
  • 2005 年 Oracle 收购 Innobase Oy
  • MySQL 5.5（2010）起成为默认存储引擎

以上为可核实的产品史。

它在 MySQL 里干什么

MySQL 是客户端 / 服务器架构。Server 层负责连接、解析 SQL、生成执行计划；真正读写记录的是存储引擎。

InnoDB 向上提供统一 API（读第一条 / 下一条、插入、加锁等），向下把数据放到磁盘页上，并提供：

  • 事务、redo / undo
  • 行级锁、MVCC
  • 聚簇索引（索引即数据）
  • 外键

关系一句话：换引擎可以换物理结构；解析与优化仍在 Server 层。本讲只沿着 InnoDB 这条路径往下走。

第 3 页 · 整体架构

InnoDB 在 MySQL 里的位置

SQL 层负责解析与优化；真正读写页、索引、事务和日志的是 InnoDB。换引擎可以换物理结构，本讲只沿着 InnoDB 这条路径往下走。

第一部分

InnoDB 每条记录
如何编码

先看 Compact 行格式：变长长度、NULL 位图、记录头，以及隐藏列。

第 5 页 · Compact 行格式

一条记录 = 额外信息 + 真实数据

InnoDB 平时按记录读写，落盘时先按行格式编码。Compact 把一行拆成两段：左额外信息、右真实数据。额外信息共三块——变长字段长度列表、NULL 值列表、记录头。本页把前两块讲清楚。

从左到右：变长长度列表 → NULL 值列表 → 记录头（5 字节）→ 各列真实数据。

1. 变长字段长度列表

  • 对象是 VARCHAR、VARBINARY、TEXT、BLOB。L = 本行该列实际占用的字节数，不是字符个数。
  • 写在记录开头，按列在表中的顺序逆序存放。例如 c4、c2、c1 → 01 03 04。
  • 值为 NULL 的变长列不进入这份列表。
  • 记 L 用几个字节，先看列定义上限 M×W（M 是 VARCHAR(M) 的最大字符数，W 是一个字符最多几个字节）：
    • 上限 ≤ 255：永远 1 字节，不必看 L。
    • 上限 > 255：再看本行的 L。L ≤ 127 仍 1 字节，L > 127 才 2 字节（第一字节最高位当续字节标志，所以门槛是 127 不是 255）。
  • 定长字符集下的 CHAR(M) 不进列表；变长字符集下的 CHAR(M) 按变长列处理。

2. NULL 值列表

  • 先数表里允许为 NULL 的列。带 NOT NULL 的列、主键都不参与；一张表若没有可空列，这条列表直接省略。
  • 每个可空列占 1 bit：1 表示该列是 NULL，0 表示非空。二进制位同样按列顺序逆序排放。
  • 必须凑成整字节，缺的高位补 0。例如 3 个可空列只需 1 字节；9 个可空列就要 2 字节。
  • 两条记录对照：三列皆非空 → 0x00；c4、c3 为 NULL → 二进制 00000110 = 0x06。
  • Compact 下，值为 NULL 的列不再写入真实数据区，所以变长列表里也没有它的长度。

第 6 页 · 实例

两条记录的完整 Compact 编码

CREATE TABLE record_format_demo ( c1 VARCHAR(10), c2 VARCHAR(10) NOT NULL, c3 CHAR(10), c4 VARCHAR(10) ) CHARSET=ascii ROW_FORMAT=COMPACT; INSERT INTO record_format_demo VALUES ('aaaa', 'bbb', 'cc', 'd'), ('eeee', 'fff', NULL, NULL);
  • ascii：1 字符 = 1 字节。c1、c3、c4 允许 NULL，c2 不允许。
  • 未定义主键，真实数据前有 row_id 6B、trx_id 6B、roll_pointer 7B。
  • CHAR(10) 固定占 10 字节，不足补空格 0x20，长度不进变长列表。
  • NULL 列只记在 NULL 值列表，真实数据区不再占位。

第一部分（续）

InnoDB 数据页结构

页是 16KB 的盒子。记录按行格式放进 User Records，再用链表和页目录来找。

第 8 页 · 页内布局

一个数据页被切成七段

默认 16KB。File Header 与 File Trailer 是各类页通用的；中间五段是数据页专有的。

  1. File Header　38 字节各类页通用。页号、页类型（数据页是 FIL_PAGE_INDEX）、前后页号把数据页串成双向链表，还有校验和。
  2. Page Header　56 字节数据页专有状态：槽数、记录数、堆顶地址、已删记录的垃圾链表、最后一次插入的位置。
  3. Infimum + Supremum　26 字节两个伪记录，分别代表本页最小、最大。用户记录按主键夹在中间。它们也是行记录，但不是用户插入的。
  4. User Records　大小不定真正存放插入行的地方，按 Compact 等行格式编码。新页生成时这一段还不存在。
  5. Free Space　大小不定尚未使用的空间。每插入一行，就从这里切出一块划给 User Records。
  6. Page Directory　大小不定页目录。每个槽记下某一组最后一条记录的页内偏移，查找时先对槽二分。记录越多，槽越多。
  7. File Trailer　8 字节各类页通用。前 4 字节校验和、后 4 字节 LSN，用来判断页从内存写回磁盘时有没有写完整。

第 9 页 · 插入过程

记录从空闲区一块块长进页里

新页

生成时没有 User Records。File Header、Page Header、Infimum + Supremum、Page Directory、File Trailer 已经就位，中间几乎全是 Free Space。

每插一条

从 Free Space 申请一块与该行同样大小的空间，划进 User Records。记录在页里紧挨着放，没有空隙。

插满

Free Space 被 User Records 吃光，这一页用完。再插入就要申请新页。页目录也会随记录增多，从尾部往上长。

第 10 页 · 记录头与伪记录

每个页先有两条伪记录：最小 Infimum、最大 Supremum

以表 page_demo(c1 INT 主键, c2 INT, c3 VARCHAR) 为例：Compact 行的记录头固定 5 字节（40 bit）。为方便看头信息，图里只画出头字段和 c1、c2、c3；隐藏列仍在，只是省略。

为什么 heap_no 没有 0 和 1？

InnoDB 给每个数据页自动加两条伪记录（虚拟记录），不经过 INSERT，也不放在 User Records。

Infimum　最小记录 heap_no = 0　record_type = 2 5 字节头 + 固定 8 字节 infimum\0
Supremum　最大记录 heap_no = 1　record_type = 3 5 字节头 + 固定 8 字节 supremum
头 5B infimum\0　8B 头 5B supremum　8B
  • 完整记录比大小 = 比主键。用户行主键可以是 1、2、3…，但规定这两条永远是本页最小 / 最大。
  • 二者合在 Infimum + Supremum 段，固定 26 字节，不进入 User Records。

next_record 按主键把行串成链，不是按插入顺序

为什么指针落在「头和数据交界」

  • 向左读 5 字节头，向右读真实数据。变长列表、NULL 列表逆序存放，靠前的列和它的长度在内存里更近。
  • 沿链找主键时，当前节点已经比目标大就可以停，后面只会更大。
  • 行少时从 Infimum 一路扫也行；行多了就慢——所以下一页做页目录。

第 12 页 · 页目录与槽

组的最后一条记进槽，查找先对槽二分再扫一组

再插入 12 行后共 18 条（含最小、最大），分成 5 组。每个槽指向该组最后一条（组内主键最大）的页内偏移，每个槽 2 字节，靠页尾存放。

目录怎么做成

  1. 把所有正常记录分组（含最小、最大，不含已删）。
  2. 每组最后一条的 n_owned = 组内条数；组里其他行的 n_owned 为 0。
  3. 把这条记录的地址偏移按序写入 Page Directory。这些偏移叫槽 Slot。槽 0 靠近页尾，对应最小记录。

每组允许多少条

  • 最小记录那一组：只能 1 条（它自己）。
  • 最大记录那一组：1～8 条。
  • 其余组：4～8 条。
  • 新页只有最小、最大，各占一组。之后插入：找到「主键刚好比新行大」的那个槽，把该槽的 n_owned +1。
  • 某组到 8 条后再插入：拆成 4 条和 5 条，页目录新增一个槽。

查找主键 6（槽编号 0～4）

  1. 二分：mid=(0+4)/2=2，槽 2 对应主键 8，8>6，故 high=2。
  2. mid=(0+2)/2=1，槽 1 对应主键 4，4<6，故 low=1。high−low=1，目标在槽 2 那一组。
  3. 槽指向组内最大行，所以先取槽 1 的记录（主键 4），它的下一条就是槽 2 组内最小行（主键 5），再沿 next_record 扫到 6。一组最多 8 条，扫得起。

第二部分

B+ 树索引

目录项也是记录，也放进 16KB 的页。多级目录就是 InnoDB 的 B+ 树。

第 14 页 · B+ 树存储结构

InnoDB 用数据页把目录套成一棵 B+ 树

以表 index_demo(c1 INT 主键, c2 INT, c3 CHAR(1)) 为例。页号可以不连续（10 之后是 28）。每个节点都是同样的数据页（类型 FIL_PAGE_INDEX），都能用页目录二分。

蓝块 2 / 3 是每页的 Infimum、Supremum。红块是主键 c1，灰块是 c2，橙块是 c3。叶页之间的蓝箭头是双向链表。

为什么要多级目录

  • 单页里可以槽二分；很多页时，若不建目录，只能沿页的双向链表从头扫。
  • 简易做法是把「每页最小主键 + 页号」排成数组。页会增删、物理上也不连续，数组搬移太笨。
  • 目录项长得像记录，于是复用数据页来存，叫目录项记录。record_type = 1。

对着这张图读三层

  • 叶子（第 0 层）：页 10、28、9、20、31。普通用户记录，record_type = 0。页内主键单链表，页间主键双向链表；下一页主键必大于上一页。
  • 内节点：页 30、32。目录项 = 该子树最小主键 + 页号。页 30 指向 10 / 28 / 9 / 20，页 32 指向 31。
  • 根：页 33。[1, 320) → 页 30，≥ 320 → 页 32。根页号写入数据字典后不再移动。

查找主键 20

  1. 根页 33：20 < 320，进入页 30。
  2. 页 30：12 < 20 < 209，进入叶页 9。
  3. 页 9 里用页目录二分，找到主键 20 那一行。

粗算：叶页约 100 条、内节点约 1000 条目录。三层大约 108 行，四层已远超常见表。主键查找最多走几个页，每页再二分。

第 15 页 · 聚簇索引

聚簇索引：叶子就是整张表，按主键排好

上一页那棵树，两个特点同时成立时，就叫聚簇索引。InnoDB 自动维护，不必写 INDEX。一张表一棵：索引即数据。

特点一：处处按主键排序

  • 页内用户记录：主键升序单链表。
  • 存放用户记录的页：按页内主键双向链表。插入时若破坏「下一页主键更大」，就要页分裂、挪记录（例如主键 5 从页 10 挪到页 28）。
  • 同一层的目录项页：也按目录项主键双向链表。

特点二：叶子存完整用户记录

所有列 + 隐藏列（trx_id、roll_pointer；没有主键时还有 row_id）。在叶子页用主键就能直接取出整行，不用回表。

内节点
type=1 主键 c1 子页页号 叶子
type=0 c1 + c2 + c3 + 隐藏列

主键从哪来

  1. 有主键：按主键建聚簇索引。
  2. 没有：选第一个 NOT NULL 的 UNIQUE 列。
  3. 再没有：InnoDB 生成 6 字节隐藏 row_id，按它排序。

主键最好稳定、尽量顺序插入。乱序主键会让叶子页频繁分裂，页在磁盘上更碎。

和 MyISAM 差在哪

MyISAM 数据文件按插入序另存，索引叶子是「键 + 行号 / 偏移」，查完还要按地址取行。InnoDB 的聚簇索引叶子就是行本身。

第 16 页 · 二级索引

非主键条件要另建一棵树，叶子只有键和主键

聚簇索引按主键排，WHERE c2 = 4 不能走那棵树的目录。于是为 c2 再建一棵 B+ 树，称为二级索引（辅助索引）。

和聚簇索引的三处不同

  • 页内链表、叶页链表、同层目录页，都改按 c2 排序（c2 相同再按主键）。
  • 叶子不是完整行，只存 c2 + 主键 c1。每建一棵树若再拷整行，太占空间。
  • 目录项表面上是「c2 + 页号」。若多行 c2 都是 1，插入时不知道进哪一页。所以补上主键：内节点实际是 c2 + 主键 + 页号，同一层除页号外必须唯一。
内节点 c2 主键 c1 页号 叶子 c2 主键 c1

用 c2 = 4 查找（四步）

  1. 从这棵树的根页下降，按 c2 定位目录项页。
  2. c2 可以重复，目标行可能跨多个叶页。
  3. 在那些叶页里取出二级索引记录。
  4. 叶子只有 c2 和 c1，不够填完整行 → 拿 c1 再走聚簇索引。这一步叫回表。查一行完整记录用了 2 棵 B+ 树。

一张表可以有多棵二级索引。每插、删、改一行，聚簇和所有二级树都要维护排序，所以索引不是越多越好。

第 17 页 · 联合索引

多列也可以只建一棵树：先左列，再右列

也可以为 c2、c3 一起建索引。本质仍是二级索引，但排序规则是两列，不是两棵树。

排序规则（两层含义）

  • 各条记录、各个页，先按 c2 排。
  • c2 相同，再按 c3 排。

因此：

  • 目录项：c2 + c3 + 页号（同样必要时带主键，保证同层唯一）。
  • 叶子用户记录：c2 + c3 + 主键 c1，没有其他列。
c2 c3 主键 c1 叶子：没有其余列

例如 idx_name_birthday_phone_number(name, birthday, phone_number)：先 name，再 birthday，再电话。叶子也不存 country。

1 棵树，不是 2 棵树

联合索引 (c2, c3)分别建 idx(c2)、idx(c3)
B+ 树数量1 棵2 棵
排序先 c2，相同再 c3各按自己那一列
WHERE c2 = ?能用（最左列）走 idx(c2)
WHERE 只有 c3用不上这棵树走 idx(c3)
WHERE c2 且 c3一棵树走到底两棵树或回表后再滤

最左前缀：条件要从最左列连续用起。左边等值时，右边才可以范围。跳过中间列，右边用不上。WHERE 里写列的顺序无关，优化器会按索引列序重排。

第 18 页 · 回表

二级索引拿到的是主键，整行还要再走聚簇索引

用非主键索引查完整行，必须用 2 棵 B+ 树。第二棵就是聚簇索引，这个过程叫回表。

1. 下二级索引
从该索引根页一层层走，页内用页目录按索引列二分
→
2. 叶子只有键+主键
例如 c2 与 c1。SELECT * 或要用到未收录的列，这里不够
→
3. 拿主键回表
再从聚簇索引根页下降，在叶子取出完整用户记录
→
4. 再过滤
二级索引用不上的条件（如另一列范围）只能在整行上判断

为什么贵

  • 二级索引叶子按索引列排好，扫这一段接近顺序 I/O。
  • 相邻二级记录的主键往往不连续，回表是随机 I/O：每次几乎从聚簇根再走一遍。
  • name 落在某区间的行若占全表 90%，为这些主键回表，还不如直接扫聚簇索引（全表扫描）。

怎样少回表

  • 覆盖索引：查询列表（以及过滤用到的列）都在这棵二级索引里，叶子已经够用，Extra 里会出现 Using index，不必回表。
  • 少写 SELECT *。只要多要一列不在索引里，就要回表。
  • 加 LIMIT 能截断回表次数，优化器更愿意选「二级索引 + 少量回表」。

第三部分

MySQL 基于成本计算的优化

执行前先给每条访问路径算成本：读页是 I/O，检行是 CPU。谁便宜，就留下谁。

第 20 页 · 基于代价的优化器

成本不是秒表，是「读页 + 检行」两套常数加起来

真正执行前，优化器枚举方案、算出各自成本，留下最低的作为执行计划。一条查询的成本只由两块组成。

查询成本 = I/O 成本 + CPU 成本
I/O：把页从磁盘装进内存　·　CPU：读记录、判断条件、排序等（在内存里做）

两个最常用的成本常数

  • 页是 InnoDB 与磁盘交互的单位。读 1 个页面默认成本 1.0。
  • 读并检测 1 条记录默认成本 0.2。哪怕不用再判断条件，读一行也按 0.2 算。
  • 这两个数写在 mysql.engine_cost 一类表里，可以改，讲义按默认。

单表四步

  1. 根据 WHERE，找出可能用的索引（possible keys）。索引列与常数用 = IN > < BETWEEN LIKE 前缀 等连上，才能形成范围区间。
  2. 算全表扫描成本。
  3. 分别算各索引（含回表；必要时再看索引合并）。
  4. 取最低者作为执行计划，再调存储引擎去执行。

全表扫描怎么算

把聚簇索引叶子几乎读完，每行都拿去对条件。需要两份统计：SHOW TABLE STATUS 的 Rows（InnoDB 是估计值）和 Data_length。

聚簇页数 N = Data_length ÷ 16 ÷ 1024

I/O = N × 1.0 + 1.1　　CPU = Rows × 0.2 + 1.0

1.1 与 1.0 是代码里的微调。全表扫描按「聚簇占用的全部页」计 I/O，不区分内节点和叶子。

二级索引 + 回表怎么算

  • 优化器很粗：一个范围区间的索引 I/O 就按读 1 页 = 1.0，不管这个区间实际跨几页。
  • 区间里有 R 条二级记录：读它们的 CPU = R × 0.2 + 0.01。
  • 回表更粗：每条都当再读 1 页，I/O = R × 1.0。回表后还要检测其余条件，再加 CPU = R × 0.2。

I/O = 区间数 × 1.0 + R × 1.0

CPU = R × 0.2 + 0.01 + R × 0.2

R 的求法：在二级索引上定位区间最左、最右记录；隔得近就精确数，远就抽样平均每页条数 × 页数。

第 21 页 · 计算实例

把公式代进 single_table：谁便宜选谁

SELECT * FROM single_table WHERE key1 IN ('a', 'b', 'c') AND key2 > 10 AND key2 < 1000 AND key3 > key2 AND key_part1 LIKE '%hello%' AND common_field = '123';

possible keys 只有 idx_key1、idx_key2。key3 > key2 不是和常数比；LIKE '%hello%' 前导通配；common_field 无索引。

SHOW TABLE STATUS：Rows = 9693（实际约 10000，InnoDB 估计），Data_length = 1589248 → 页数 = 1589248 ÷ 16 ÷ 1024 = 97。

方案 A · 全表扫描

I/O　97 × 1.0 + 1.1 = 98.1

CPU　9693 × 0.2 + 1.0 = 1939.6

合计 2037.7

1 个区间 (10, 1000)。在 idx_key2 上定位两端，估得 R = 95。

I/O　1.0 + 95 × 1.0 = 96.0

第四部分

事务隔离、MVCC
与锁

先看并发会出什么错，再用版本链和 ReadView 读旧版本；写仍要排队，排队靠锁。

第 23 页 · 并发问题（一）

不串行时，先遇到脏写和脏读

以表 hero(number 主键, name, country) 为例，先有一行 (1, 刘备, 蜀)。两会话同时开事务，访问同一行时，若不排队，会出四类问题。本页先看最严重的两个。

1. 脏写 Dirty Write

改了别人还没提交的修改

  1. Session B：UPDATE name='关羽'，未提交。
  2. Session A：再把同一行改成 '张飞'。
  3. B 随后 ROLLBACK。A 已经改过、甚至提交了，这一行却像没发生过。

太严重：不论哪种隔离级别都不允许脏写。InnoDB 用锁让写写排队——第一个事务改完给记录加锁，另一个必须等它提交。

2. 脏读 Dirty Read

读到了别人还没提交的修改

  1. Session B：把 name 改成 '关羽'，未提交。
  2. Session A：SELECT 读到了 '关羽'。
  3. B 回滚。A 等于读到了一条后来不存在的数据。

SQL 标准：READ UNCOMMITTED 允许脏读；READ COMMITTED 及以上不允许。MySQL 默认是 REPEATABLE READ。

严重程度：脏写 > 脏读 > 不可重复读 > 幻读。隔离级别越低，越严重的问题越可能发生。脏写不靠 ReadView，靠锁；后三种靠 MVCC（或锁定读）。

第 24 页 · 并发问题（二）

接着是不可重复读，以及多出来的「幻影行」

3. 不可重复读 Non-Repeatable Read

同一行，两次读到的已提交值不一样

  1. Session A 开启事务，先读 number=1，看到 刘备。
  2. Session B 用隐式事务（语句结束就提交）把 name 改成关羽、张飞……
  3. A 再用同一条 SELECT，每次都能读到 B 刚提交的最新值。

前提是只读已提交的修改（所以不是脏读），但本事务里同一行的结果不稳定。

READ COMMITTED 允许；REPEATABLE READ 不允许。

4. 幻读 Phantom

同一条件，第二次读出了以前没有的行

  1. Session A：SELECT * FROM hero WHERE number > 0，只有刘备。
  2. Session B 插入一行新记录并提交。
  3. A 按相同条件再查，结果集里多出 B 插入的那一行。

幻读指读到了之前没有的记录。若 B 删了若干行导致 A 第二次变少，那是对那些行发生了不可重复读，不算幻读。

SQL 标准里 RR 仍可能幻读；MySQL 默认 RR 下，普通 SELECT 用 ReadView 已经能禁止幻读。

隔离级别脏读不可重复读幻读
READ UNCOMMITTED可能可能可能
READ COMMITTED不可可能可能
REPEATABLE READ（SQL 标准）不可不可可能
SERIALIZABLE不可不可不可

第 25 页 · ReadView

后三种问题：沿着 undo 版本链，用 ReadView 挑可见版本

改一行会把旧值写入 undo，roll_pointer 串成版本链，头是最新版，每版带着 trx_id。未提交读直接看最新；可串行化靠加锁。已提交读、可重复读必须从链上挑「当前事务该看见」的那一版——工具就是 ReadView。

快照里四项

  • m_ids：生成时系统里还活跃的读写事务 id 列表。
  • min_trx_id：上述列表里的最小值。
  • max_trx_id：生成时下一个将要分配的事务 id（不是 m_ids 的最大值）。
  • creator_trx_id：生成这个 ReadView 的事务自己的 id；只读事务一般为 0。

某版本的 trx_id 是否可见

  1. 等于 creator_trx_id：自己改的，可见。
  2. 小于 min_trx_id：生成快照前已提交，可见。
  3. 大于 max_trx_id：快照之后才开的事务，不可见。
  4. 落在中间：在 m_ids 里则当时还活跃，不可见；不在则当时已提交，可见。

不可见就沿 roll_pointer 找下一个版本，直到可见或整条链都不可见。

生成时机不同，挡住的问题不同

READ COMMITTED：每次普通 SELECT 都新生成一个 ReadView。未提交的 trx 在 m_ids 里，最新版不可见，于是不会脏读。对方提交后再 SELECT，快照里没有它了，就能看见新值 → 仍可能不可重复读、幻读。

例如：活跃事务 100、200，RC 第一次读到「刘备」；100 提交后第二次读到「张飞」。

REPEATABLE READ：只在第一次普通 SELECT 时生成 ReadView，之后一直复用。对方后来提交的修改、后来插入的行，trx_id 要么仍在当时的 m_ids，要么 ≥ 当时的 max_trx_id，都不可见 → 普通 SELECT 下脏读、不可重复读、幻读一并挡住。

这就是 MVCC：RC / RR 下普通 SELECT 走版本链，读写不必互相堵。写最新版、读历史版不冲突。脏写仍要靠下一页的锁。

第 26 页 · 共享锁与独占锁

写要排队：读加 S 锁，改加 X 锁

读读无事。写写必须排队，否则脏写。读写若不许看旧版本，也要排队。排队的手段就是锁——内存里的结构，一开始记录上并没有锁。

两种行锁

  • S 锁（Shared）：要读一行时获取。已有 S 时，别人还能再拿 S，不能拿 X。
  • X 锁（Exclusive）：要改一行时获取。已有 X 时，别人拿 S 或 X 都要等该事务提交。
兼容性XS
X不兼容不兼容
S不兼容兼容

锁定读（不是普通 SELECT）

  • SELECT ... LOCK IN SHARE MODE：给读到的行加 S。
  • SELECT ... FOR UPDATE：给读到的行加 X。

RC / RR 下普通 SELECT 是一致性读（快照读），不加锁。锁定读读的是最新版。

加锁成功 / 失败

  • 内存里生成锁结构，is_waiting=false：加锁成功，事务继续。
  • is_waiting=true：加锁失败，线程等待；对方提交后把自己的锁释放，再把等待者唤醒。

写语句怎么锁

  • DELETE / 多数 UPDATE：在 B+ 树定位到该行后加 X 锁，再改。
  • INSERT 一般不显式加锁，靠记录上的 trx_id 当隐式锁；别人再加 S/X 时，会先帮插入事务补一个 X 锁结构，自己再等待。

表上也有 S / X

行锁前先在表上放意向锁：准备加行 S 先加表 IS，准备加行 X 先加表 IX。这样给整表加 S/X 时，不用扫每一行，看门口有没有 IS/IX 即可。

第 27 页 · InnoDB 内存锁

加锁不是给每行建一个对象，而是页内共用一个结构

对一行加锁，本质是在内存里挂一个锁结构。若同一事务、同一页面、同一锁类型、同一等待状态，多行可以塞进同一个结构，用末尾一堆比特位区分是哪几行。

锁结构里有什么

  • 事务信息、行锁还有索引信息：实际是指针。
  • 行锁再记：表空间号 Space ID、页号 Page Number、n_bits（末尾用了多少比特）。
  • n_bits 会比页里现有记录多留一些（公式里有固定余量 64），免得插入新行就重建结构。
  • 末尾比特位按记录的 heap_no 映射：Infimum=0，Supremum=1，之后插入的行递增。哪一位为 1，哪一行被这个结构锁住。

type_mode（32 位打包）

  • 低 4 位 lock_mode：IS=0，IX=1，S=2，X=3，AUTO-INC=4。
  • 第 5～6 位 lock_type：TABLE=16，REC=32。
  • 第 9 位 LOCK_WAIT=256：就是 is_waiting。
  • 其余是行锁细分：next-key=0，GAP=512，正经记录锁 REC_NOT_GAP=1024，插入意向=2048。

同一页上的例子

T1 对 number=15 加 S 型正经记录锁：一个结构，type_mode = LOCK_S | LOCK_REC | LOCK_REC_NOT_GAP = 2|32|1024 = 1058，对应 heap_no 那一位置 1，等待位为 0。

T2 想对 number=3、8、15 加 X 型 next-key。3 和 8 无人占用，可以马上拿到；15 已被 T1 的 S 挡住。等待状态不同，于是 T2 生成两个锁结构：一个 is_waiting=false 罩住 3 和 8，一个 is_waiting=true 罩住 15。

所以「给 10000 行加锁」并不等于 10000 个对象：能合并的合到同一页、同一等待状态的一个结构里，用位图标记行。
